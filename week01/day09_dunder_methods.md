## 1. What Dunder Methods Are

Dunder is short for **d**ouble **under**score, as in `__init__`. These special methods let your objects work with Python's built-in syntax and functions.

Python's operators and built-ins call these methods behind the scenes:

| You write | Python calls |
|---|---|
| `print(obj)`, `str(obj)` | `obj.__str__()` |
| `repr(obj)`, or showing it in the console | `obj.__repr__()` |
| `a == b` | `a.__eq__(b)` |
| `a < b` | `a.__lt__(b)` |
| `a + b` | `a.__add__(b)` |
| `len(obj)` | `obj.__len__()` |
| `obj[key]` | `obj.__getitem__(key)` |
| `x in obj` | `obj.__contains__(x)` |
| `for x in obj` | `obj.__iter__()` |
| `if obj:` | `obj.__bool__()`, or `__len__` if `__bool__` isn't defined |
| `obj()` | `obj.__call__()` |
| `hash(obj)`, using it as a dict key or in a set | `obj.__hash__()` |

This is how `len()` works on lists, strings, and dicts alike: each type has its own `__len__`.

## 2. `__str__` vs `__repr__`

```python
class User:
    def __init__(self, name, role):
        self.name = name
        self.role = role

u = User("Dileep", "dev")
print(u)    # <__main__.User object at 0x000001A2B3C4D5E6>  — useless
```

```python
class User:
    def __init__(self, name, role):
        self.name = name
        self.role = role

    def __repr__(self):
        return f"User(name={self.name!r}, role={self.role!r})"

    def __str__(self):
        return f"{self.name} ({self.role})"

u = User("Dileep", "dev")
print(u)          # Dileep (dev)                     ← __str__
print(repr(u))    # User(name='Dileep', role='dev')  ← __repr__
print([u])        # [User(name='Dileep', role='dev')] ← lists use __repr__
```

| | `__repr__` | `__str__` |
|---|---|---|
| Audience | Developers: debugging and logs | End users |
| Goal | Unambiguous, ideally valid code that recreates the object | Readable |
| Used by | The console, lists and dicts, `{x!r}` in f-strings | `print()`, `str()`, `{x}` in f-strings |
| If missing | Python's default `<User object at ...>` | Python falls back to `__repr__` |

> **Rule:** if you only write one, write `__repr__`. You'll be grateful every time you debug.

`!r` (Day 1) adds quotes around strings so you can see exactly what the value is.

## 3. Equality and Hashing

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

print(Point(1, 2) == Point(1, 2))   # False! default == compares identity (like `is`)
```

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented          # let Python try the other side
        return (self.x, self.y) == (other.x, other.y)

    def __hash__(self):
        return hash((self.x, self.y))      # hash the same fields used in __eq__

print(Point(1, 2) == Point(1, 2))          # True
print({Point(1, 2), Point(1, 2)})          # one item — duplicates removed
```

### The `__eq__` and `__hash__` rule (important interview question)

- If you define `__eq__` without `__hash__`, Python sets `__hash__` to `None`. Your objects then can't be put in a set or used as dict keys, and you get `TypeError: unhashable type`.
- **The rule:** if two objects are equal, they must have the same hash. Build the hash from the same fields you compare in `__eq__`.
- Only make objects hashable if those fields won't change. If an object's hash changes while it's inside a set, the set can no longer find it.

This connects to Day 3: dict keys must be hashable, and that's exactly what `__hash__` provides.

`NotImplemented` (not `NotImplementedError`) tells Python "I don't know how to compare with this type," so Python tries the other object's method. If neither side knows, `==` falls back to identity (so it's usually `False`), while `<` raises a `TypeError`.

## 4. Ordering and `@total_ordering`

```python
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, major, minor):
        self.major = major
        self.minor = minor

    def __eq__(self, other):
        return (self.major, self.minor) == (other.major, other.minor)

    def __lt__(self, other):
        return (self.major, self.minor) < (other.major, other.minor)

    def __repr__(self):
        return f"Version({self.major}, {self.minor})"

print(Version(1, 2) < Version(1, 10))     # True
print(Version(2, 0) >= Version(1, 9))     # True — generated by @total_ordering
print(sorted([Version(2, 0), Version(1, 5), Version(1, 10)]))
# [Version(1, 5), Version(1, 10), Version(2, 0)]
```

`@total_ordering` generates `<=`, `>`, and `>=` from your `__eq__` and `__lt__`. Comparing tuples (Day 4's sorting trick) makes `__lt__` a one-liner.

This also shows why `"1.10" < "1.2"` is `True` for strings: strings compare character by character. Comparing numbers in tuples gives the correct order.

## 5. Making Container-like Objects

```python
class Playlist:
    def __init__(self, name):
        self.name = name
        self._songs = []

    def add(self, song):
        self._songs.append(song)

    def __len__(self):
        return len(self._songs)

    def __getitem__(self, index):
        return self._songs[index]          # passes through indexes AND slices

    def __contains__(self, song):
        return song in self._songs

    def __iter__(self):
        return iter(self._songs)

p = Playlist("Focus")
p.add("Song A"); p.add("Song B"); p.add("Song C")

print(len(p))            # 3
print(p[0], p[-1])       # Song A Song C
print(p[1:])             # ['Song B', 'Song C']
print("Song B" in p)     # True
for song in p:           # works because of __iter__
    print(song)
if p:                    # truthy because __len__ > 0
    print("not empty")
```

Your class now behaves like a built-in collection. Python calls this **duck typing**: "if it walks like a duck and quacks like a duck, it's a duck." Code that loops over a list will also work with a `Playlist`, because it only needs `__iter__`.

You'll learn how to write `__iter__` yourself using generators on Day 11.

## 6. Arithmetic Operators and `__call__`

```python
class Money:
    def __init__(self, amount, currency="INR"):
        self.amount = amount
        self.currency = currency

    def __add__(self, other):
        if self.currency != other.currency:
            raise ValueError("Currency mismatch")
        return Money(self.amount + other.amount, self.currency)   # NEW object

    def __repr__(self):
        return f"Money({self.amount}, {self.currency!r})"

print(Money(100) + Money(50))     # Money(150, 'INR')
```

`__add__` should return a new object and leave the original unchanged, the same way `1 + 2` doesn't change `1`.

### `__call__`: making an object callable like a function

```python
class Multiplier:
    def __init__(self, factor):
        self.factor = factor

    def __call__(self, x):
        return x * self.factor

double = Multiplier(2)
print(double(5))      # 10 — the object is called like a function
```

This is useful for objects that need to remember settings between calls. Class-based decorators, which you'll see on Day 10, use `__call__`.

## 7. Properties

`@property` lets you run code when an attribute is read or set, while callers still use normal `obj.attr` syntax. It's the Pythonic replacement for `get_x()` and `set_x()` methods.

### Validating on assignment

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary          # goes through the setter below!

    @property
    def salary(self):                 # getter
        return self._salary

    @salary.setter
    def salary(self, value):          # setter
        if value < 0:
            raise ValueError("Salary cannot be negative")
        self._salary = value

e = Employee("Dileep", 100)
print(e.salary)        # 100 — looks like a normal attribute
e.salary = 200         # runs the setter → validated
e.salary = -5          # ValueError
```

Notice that `__init__` assigns `self.salary`, not `self._salary`, so the validation also runs when the object is created. The real value is stored in `_salary`, using the underscore convention from Day 8.

> **Common bug:** if the setter does `self.salary = value` instead of `self._salary = value`, it calls itself forever and raises `RecursionError`.

### Computed and read-only properties

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    @property
    def area(self):                   # computed every time — always up to date
        return self.width * self.height

r = Rectangle(3, 4)
print(r.area)        # 12 — no () needed
r.width = 10
print(r.area)        # 40 — updates automatically
r.area = 50          # AttributeError — no setter, so it's read-only
```

Why not just use a normal attribute? If `area` were set once in `__init__`, it would become wrong as soon as `width` changed. A property is always calculated from the current data.

**Why properties matter:** you can start with a plain attribute and later turn it into a property with validation without changing any code that uses it. In Java, people write getters and setters up front for this reason; in Python, you don't need to.

## 8. Abstract Classes

An abstract class defines methods that its children must implement. You can't create an object from the abstract class itself.

```python
from abc import ABC, abstractmethod

class LLMProvider(ABC):
    @abstractmethod
    def generate(self, prompt: str) -> str:
        """Return the model's response."""

    def generate_upper(self, prompt: str) -> str:   # normal method — shared by all
        return self.generate(prompt).upper()

class AzureOpenAIProvider(LLMProvider):
    def generate(self, prompt: str) -> str:
        return f"[azure] {prompt}"

class MockProvider(LLMProvider):
    def generate(self, prompt: str) -> str:
        return "mock response"

# LLMProvider()          # TypeError: Can't instantiate abstract class
provider = AzureOpenAIProvider()
print(provider.generate_upper("hello"))   # [AZURE] HELLO
```

If a child class forgets to implement `generate`, Python raises a `TypeError` when you create the object, not later when the method is called in production. That catches the mistake early.

**Why use them:**

- They define a contract that every implementation must follow
- Code can depend on `LLMProvider` without knowing which provider it's using, which is polymorphism from Day 8
- For tests, swap in `MockProvider` instead of calling the real API (Week 8)

This is a very realistic pattern for agent platforms: LLM providers, vector stores, and tools often follow it, and LangChain's base classes work this way too.

### `Protocol` (awareness)

```python
from typing import Protocol

class Greeter(Protocol):
    def greet(self) -> str: ...

class English:                  # does NOT inherit from Greeter
    def greet(self) -> str:
        return "Hello"

def welcome(g: Greeter) -> None:
    print(g.greet())

welcome(English())   # fine — it has the right method
```

| | `ABC` | `Protocol` |
|---|---|---|
| Child classes must inherit from it | Yes | No |
| Checked when | You create an object | By type checkers such as mypy, not at runtime |
| Style | Explicit contract | Formalized duck typing |

> **Rule:** use `ABC` when you own all the implementations and want a runtime check. Use `Protocol` when you want to accept any object that has the right methods.
